## 3. Crash found and fixed: GX FIFO "draw vertex data overrun" (observed + asm-proven)

- Symptom: `[aurora::gx::fifo] draw vertex data overrun: need N bytes at pos P, have M`, process aborts (0xC0000409).
  Seen at ~183 s in the title/movie loop (`obs1`, thp=2) and at ~204 s (tick 6120) in airport0 (`r07b..r07e`, same position
  77590 every time, i.e. deterministic).
- Method: patch 0008 (below) recorded the last parsed draws and, per `GXBegin`, the caller address and absolute stream
  offset. The failing position was exactly the end of a 4-vertex quad whose next 100 bytes were five more 20-byte
  vertices. Caller (`llvm-symbolizer`, module base from the log): `JPADrawExecRotDirectionalCross::exec`,
  `JPADrawVisitor.cpp:909`.
- Cause: the decomp had `GXBegin(GX_QUADS, GX_VTXFMT0, 4)` but writes 8 vertices (two crossed quads). Retail passes 8
  (`li r5, 0x8`, asm 0x8007C864 `RotDirectionalCross`, 0x8007C2C4 `DirectionalCross`). On hardware the count is what the
  FIFO parser trusts, so this was a real decomp bug that the 99 % score hid.
- Fix: both calls now pass 8 (`sms/src/JSystem/JParticle/JPADrawVisitor.cpp`, `// asm` comments). A scan of all
  `GXBegin` calls with a literal count against the number of `GXPosition*` calls found only these two (the third hit,
  `JUTRomFont.cpp:119`, is a false positive: 4 positions + 4 texcoord calls).
- **Not yet confirmed**: after the fix, run `r07f` was stopped by the end of the session at tick 5880 (196 s), i.e. before the
  point where the old crash occurred (tick 6120, 204 s). No crash was seen up to that point. Re-run
  `python tools/route.py Strict tools/routes/07_airport.dev --name <n> --seconds 330` and look for `overrun`.
  The title-loop crash at 183 s (`obs1`) may or may not be the same cause (it happened with no Mario/stage loaded).
- Aurora patch **0008** `0008-gx-fifo-desync-diagnostics.patch` (+112/-0, 4 files): on overrun the parser prints the last
  8 parsed draws (with vertex layout snapshot) and the `GXBegin` neighbours of the failing absolute stream position with
  caller addresses and the module base. Diagnostics only. `tools/make_aurora_patch.py` regenerates such a patch from the
  working tree. Symbolise with
  `llvm-symbolizer --obj=build/Strict/sunshine.exe --relative-address <caller - module base>`.

## 5. Environment notes learned

- Git Bash rewrites `cmd /c`'s `/c` into `C:\`: run `_strict.cmd` from PowerShell:
  `python tools\locked.py cmd /c tools\_strict.cmd`.
- A game run started with `( ... &)` from the tool shell was killed when the call ended; use the harness's background
  mechanism. If a run dies, the run lock is left behind: `python tools/runlock.py release lead` (only when no
  `sunshine.exe` of yours is running; otherwise the next run waits up to 10 minutes and steals after 15).
- `build/Strict` (the tree `route.py` runs) is built by `tools\_strict.cmd` and includes the dev script code.
- Line endings: `devscript.cpp` is LF in the index; do not rewrite files through tools that translate to CRLF
  (the working copy had been mixed before this session; it is LF now).
