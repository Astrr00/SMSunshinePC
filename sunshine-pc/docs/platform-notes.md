## Timing

- `TApplication::gameLoop()` (`src/System/Application.cpp`) calls `TDisplay::startRendering()`, `mDirector->direct()` (logic and drawing in one pass), then `TDisplay::endRendering()` once per iteration.
- `TDisplay` is constructed with `2` in `TApplication::initialize()` (`unk4C`). `endRendering()` calls `TVideo::waitForRetrace(unk4C)`. At 60 Hz VI that is 30 logic frames per second. To confirm: the value may change per scene, and PAL (GMSP01) runs at 50 Hz.
- `TVideo::waitForRetrace` blocks on `VIGetRetraceCount()` / `VIWaitForRetrace()`. Replacing this loop is the hook for decoupled rendering.
- Other VI wait loops: `JUTConsole`, `JUTException` (debug only, irrelevant for the port).
- Logic and rendering are not separated. Interpolation therefore needs per-logic-frame snapshots of object matrices and the camera, not a faster game loop.

## SDK layer

- `sms/include/dolphin/*` is the decomp's own header set; Aurora ships its own. Which one wins when linking game code is an open decision for phase 2.
- `sms/src/main.cpp`: `gpApplication.initialize(); proc(); finalize();`. This is the entry point `sunshine-pc/src/main.cpp` will call later.
- `initialize()` uses `OSProtectRange` with fixed addresses (`0x80000000`, `0x83000000`). Those calls cannot work on PC and must go under `TARGET_PC`.

### Open items (each fails visibly instead of being faked)

- **`__fres`** (reciprocal estimate): declared without a definition in `pc_compat.h`, so `JPAField`, `JPAMath`, `MathUtil` and `J3DPSCalcInverseTranspose` fail at link time. Needs the bit-exact Gekko estimate table. Aurora has none; Dolphin's is GPL-2.0 and is not copied into this CC0/MIT-licensed port. Options: derive it from hardware test vectors, or contribute it to Aurora next to its `frsqrte`.
- **Global `operator new/delete`**: `JKRHeap.cpp` defines only the placement overloads under `TARGET_PC`. Plain `new`/`delete` in game code goes to the CRT heap and a `delete` of a JKR-allocated object would be wrong. Goal-Port B.4 (`JKR_NEW`/`JKR_DELETE`, as Dusklight) must convert every call site.
- **Paired-single math**: the `ps_madd` family is modeled with `fmaf` (one rounding). Not verified against hardware or Dolphin. `fmuls`/`ps_muls` with a double operand (frsqrte result) round that operand to 25 bits first, as on the console.
- **Float contraction**: MWCC builds the game with `-fp_contract on` and fuses multiply-adds at optimizer level. clang-cl's `-ffp-contract=on` only fuses inside one expression and needs `-mfma` to emit FMA at all. Results can differ in the last bit. Decide the flag policy before validating gameplay math.
- **Pointer truncation**: `JSUConvertOffsetToPtr` (`JSupport.hpp`) computes `(s32)ptr + offset`, and `J3DMaterial.hpp` compares `(uintptr_t)mMaterialAnm < 0xC0000000`. Both assume 32-bit pointers and are part of Goal-Port B.3 (file formats).
- **`OSf32tos8`**: saturating truncation in `pc_compat.h`; NaN behavior unverified.

52 source files are empty (621,444 code bytes, 2,068 functions, 17.3% of all code; mostly Enemy: BossHanachan*, Kukku, TabePuku, BathtubPeach, ...). They still have to be written. Without them the game cannot be completed.

## File formats on the host: RARC archives and Yaz0/Yay0

Disc data is big-endian and overlaid by structs. Each format swaps itself in place once, at the function where its raw bytes first exist, under `TARGET_PC` (helpers: `sms/include/hostendian.h`).

- **RARC** (`JKRArchive::hostSwapHeader`/`hostSwapInfoBlock`/`hostBuildFileEntries`, `JKRArchivePri.cpp`): called from `JKRMemArchive::open` (both overloads), `JKRDvdArchive::open`, `JKRAramArchive::open` and `JKRCompArchive::open` (both the plain/Yaz0 and the Yay0 branch), right after the header and the info block were read or decompressed. Header: idempotent through its own signature (reads `'RARC'` only after the swap). Info block, directory nodes and file records: idempotent through `SArcDataInfo::_1B[4]` (padding, zero on every disc archive; a fresh load from disc zeroes it again). The opaque file payloads and the string table are never touched; nested formats swap themselves.
- **`SDIFileEntry`** is 0x14 bytes on disc but 0x18 on the host (`void* mData`). The swapped 0x14-byte records stay in the buffer only as a source; `mFileEntries` points at a `calloc`ed host array (`mHostFileEntries`, `mData` starts null) that every reader indexes, freed in `unmountFixed` and `~JKRArchive`.
- **Yaz0/Yay0**: the stream decoders read the expanded size big-endian (`JKRDecomp::decodeSZS`, and the file-static `decompSZS_subroutine` in `JKRDvdRipper.cpp`, `JKRDvdAramRipper.cpp`, `JKRAram.cpp`). `decodeSZP` and `JKRDecompExpandSize` were already byte-wise.
- **`*.bti` files**: BTI headers are read raw by ~50 callers, so every `fetchResource` variant (Mem/Dvd/Aram/Comp) calls `JKRArchive::hostSwapFetchedFile` once the file bytes exist; for a file named `*.bti` it runs `swapResTIMG` (idempotent by the header marker, skipped for still-compressed data). This is a deliberate exception to "nested formats swap themselves": there is no single BTI entry point.
- **`JKRFileLoader::fetchVolumeName`** used `_tolower`, which is the unconditional `c + 0x20` macro on the MSVC CRT; it uses `tolower` on the host.
- **Check**: `tools\build-alt.cmd <name>`, `tools\rarc_test.cmd <name>`, `python tools\verify-rarc.py <name>` compare the real decoders and `JKRMemArchive` listing (paths, sizes, CRCs of every file) with an independent Python Yaz0/Yay0 decoder and RARC parser on real archives from the disc.

## File formats on the host: BTI, BFN, BLO, BMG, ResNTAB (J2D / JUT / GC2D)

Same rule as above: swap in place once where the raw bytes first exist, under `TARGET_PC`, original lines kept. Image, palette and glyph bytes are never touched (Aurora's GX converts the texels and TLUT entries itself).

- **BTI** (`ResTIMG`, 0x20 bytes on disc and on the host): `swapResTIMG()` in `JSystem/ResTIMG.hpp`, called from `JUTTexture::storeTIMG` (so every `JUTTexture`, `J2DPicture`, `J2DWindow` texture, `changeTexture`) and from the J3D TEX1 loader. Marker: byte `0x19` (`unk19`) holds `RESTIMG_HOST_MARK` (0xDE) once swapped. Raw `.bti` files have 0 there (733 of 733 on the disc, also all 2959 JPA texture headers); J3D TEX1 headers carry stray bytes there (226 distinct values in 41075 headers) but never 0xDE. A header built on the host in host order (`JUTTexture(int, int, GXTexFmt)`, `TMirrorCamera::unk94`) must set the marker itself. The marker is set after the swap and not atomically: two threads must not first-use the same unswapped resource at the same moment (the game loads in a setup thread and joins before use). Offsets stay 32-bit self-relative deltas, read as `s32`. Code that reads `JKRGetResource("*.bti")` headers directly (Map, MoveBG, Enemy, Player, NPC, MarioUtil, `hx_wiper`) must call `swapResTIMG` first; `TSMSFader` already does.
- **BFN** (`ResFONT`, INF1/WID1/MAP1/GLY1): `swapResFONT()` in `JUTFont.hpp`, called from `JUTResFont::protected_initiate`. Idempotent through the magic: `'FONTbfn1'` reads as a host `u64` equal to `RESFONT_MAGIC` only after the swap. Every field is `u8/u16/u32`, so structs keep their layout; the block walk uses the swapped block sizes. Width pairs and glyph sheets stay bytes.
- **BLO** (`J2DScreen`, `J2DPane`, `J2DPicture`, `J2DWindow`, `J2DTextBox`): not swapped in place. The readers use the typed reads of `JSUInputStream` (`readU16/readU32/readS16`, which swap on `TARGET_PC`, see the JSupport notes); the few raw reads of multi-byte scalars (`J2DPane::mKind`/`mInfoTag`, the `J2DScreen` magic/size/tag peeks) call `be32`/`be16` right after the read. Re-reading the same resource is therefore always safe. `JUtility::TColor` stores `r,g,b,a` bytes and now converts explicitly to and from the value `0xRRGGBBAA` (the console reinterpreted the bytes, which reverses the channels on a little-endian host).
- **BMG** (`TMessageLoader`, `SMSGetMessageData`): the buffer is never modified; raw reads of the file/block header words and the 12-byte entry records go through `rdbe32`/`be32`/`be16`, `SMSGetMessageData` uses typed stream reads only. Message text is plain bytes (ESC codes are ASCII). `TMessageLoader::unk8` holds 255 records and assumes 12-byte entries (as the files the game feeds it); stage/scenario/save/system BMGs have 4 or 8-byte entries and only go through `SMSGetMessageData`.
- **ResNTAB** (`JUTNameTab`, all J3D name tables): `JUTNameTab::setResource` swaps the table in place; marker `mPad0` (0xFFFF on every disc table, identical in both byte orders; swapped tables hold `RESNTAB_HOST_MARK`). `JUTNameTab(nullptr)` no longer reads address 0.
- **ResTLUT** (`JUTPalette`): only `numColors` is read, with `be16`; never written, so no marker is needed. No `.tlt` file and no TLUT reference exists on the disc.
- **Check**: `python tools\fmtcheck\fmtcheck_j2djut.py` (needs `LLVM_BIN`) builds `tools\fmtcheck\out\j2djut_check.exe` from the real decomp readers and diffs what the host structs contain against an independent big-endian parse of the same disc bytes (733 BTI, 9217 TEX1 blocks, 37289 name tables, 4 BFN incl. `getFontCode`/`getWidthEntry`, 111 BMG, 22 BLO screens with their textures/fonts/texts). Archives are extracted with `tools\fmt_arc_extract.py`.

## File formats on the host: J3D models and animations (BMD/BMT, BCK/BTK/BRK/BPK/BTP, vertex arrays)

Same rule: swap in place once, where the raw bytes first exist, under `TARGET_PC`, original lines kept. The code is header-only so it can be tested offline: `J3DSwapPC.hpp` (shared), `J3DModelSwapPC.hpp`, `J3DMatSwapPC.hpp`, `J3DAnmSwapPC.hpp` in `sms/include/JSystem/J3D/J3DGraphLoader/`.

- **Entry and marker**: `J3DModelLoaderDataBase::load/loadMaterialTable` and `J3DAnmLoaderDataBase::load` call `J3DSwapFileHeaderPC()` first. The marker is the file magic word (`'J3D1'/'J3D2'` is raw bytes that read as the byte-reversed constant before the swap), so the same buffer reaches the block conversion exactly once. The call also converts every block header and clamps `mBlockNum` to the blocks inside `mFileSize` (4 shipped `.bmt` files declare 2 blocks and contain 1). `MDL3` is not read by the decomp loader and is not converted; the only `bdl3` on the disc is not loaded by it either.
- **Table extents** come from the data: index table -> init records -> sub tables (max index + 1, clamped to the block), header counts for animations, distance to the next offset only for the inverse bind matrices. Whole elements only, each range swapped once.
- **Host size**: the block structs hold 32-bit offsets that the console relocates to pointers in place. Their members are `u32` on the host (`J3DBlockOfs`, `J3D_MAT_OFFS`, `ANM_OFS`; `JSUConvertOffsetToPtr<T>(base, u32)` converts at use). `J3DAnmVtxColorIndexData` (pointer member) is rebuilt as a host record array from an 8-byte disc record. Everything else keeps its disc size (asserted in the tests).
- **Display lists** (SHP1) stay big-endian bytes: Aurora's FIFO parser reads them as such. They contain no address words (vertex indices only; `J3DSkinDeform::initMtxIndexArray` and `DrawUtil` read them with `rdbe16`). The VCD/VAT list of a shape is generated at run time by GD into `mVcdVatCmd` (0x180 bytes on the host, Aurora's array command is 22 bytes).
- **Vertex arrays**: converted to host order at load (VTX1 arrays swapped by their VAT component type) because the game skins, mirrors and copies them on the CPU as host `s16`/`f32`. Every array is registered with Aurora as little-endian with its byte size (`GDSetArraySized` in the VCD/VAT list, `J3DLoadArrayBasePtr(attr, ptr, size)` at draw time, `J3DVertexData::getVtx*Size()`); position size = vertex count * stride, the others the span up to the next array. The matrix arrays of indexed XF loads use `GXSETARRAY(..., num * sizeof, sizeof, true)` (`J3DSys::setModelDrawMtx/NrmMtx` take the matrix count).
- **Other host fixes found on the way**: `J3DTevStage::load` writes its BP word with `rdbe32`; `loadTexNo` reads the BTI offsets as `s32`; `J3DHermiteInterpolationS` had no host branch (returned an uninitialized value); `class`/`struct` tags of forward declarations must match the definition (MSVC mangling), as must `const`/types of `extern` variables (`J3DSys.cpp` redeclared the `j3dDefault*` globals).
- **Checks** (`tools\j3d-test.cmd <test.cpp> build\j3d-corpus`; corpus from `python tools\j3d-corpus.py`): `j3d-model-test.cpp` (699 models, 23 material tables), `j3d-mat-test.cpp`, `j3d-anm-test.cpp` (1610 animation files) convert the real files and assert the format invariants (weights sum to one, unit normals, every display-list vertex index inside its array, table indices inside tables, key tables inside their arrays, ...). `tools\j3d-load-test.cmd <build name>` runs the real loaders from `sms_game.lib` (blocks, factories, materials, shapes, hierarchy, VCD/VAT lists, BCK evaluation) against an independent parse of the raw bytes: 698 models, 23 tables, 1244 BCK and all BTK/BRK/BTP/BPK, 0 failures. Unverified against real data: MAT2 layout, BCA/BPA/BVA/BLK/BLA/BXK/BXA (no samples on the disc; synthetic files only).

## File formats on the host: JAudio (AAF, sound tables, BNK, WSYS, BARC, .bas, AFC, sequences)

Same rule as above, with one addition: parsers that copy their data out never modify the buffer. Their disc structs use `DiscU16/DiscS16/DiscU32/DiscS32/DiscF32` member types (`JSystem/JAudio/JASystem/JASHostFmt.hpp`): the plain scalar on the console, `BE<T>` (`hostendian.h`, same size and layout, converts on read) on the host. All offsets stay `u32` (`JSUConvertOffsetToPtr<T>(base, u32)`). The disc only has one audio archive, `data/nintendo.szs` -> `/audi/mSound.aaf` (368288 bytes; `TApplication::initialize_bootAfter` reads it from the mounted archive and `MSound` passes it as the init-data pointer, load switch 4).

- **AAF** (`JAIBasic::checkInitDataOnMemory`, TARGET_PC rewrite; the console version stays under `#else`): a list of big-endian u32 command words, ended by 0, blobs addressed by file offset: `1 {ofs,size,0}` sound info table (a non-zero third word means three separate tables), `2 {ofs,size,waveBankNo}... 0` IBNK banks, `3 {ofs,size,loadTiming}... 0` WSYS wave banks, `4` BARC sequence archive header, `5` stream list, `6` sound scene table, `7` fx scene table, `8` unk78 (absent). The console code copies raw 12-byte records and relocates offsets to 32-bit pointers in place; the host reads word by word (`rdbe32`) and rebuilds `FabricatedBankEntry`/`FabricatedWaveBankEntry` arrays (8-byte pointers), the sound scene pointer array and the seq archive/stream list headers as host records. Blobs that are copied out (`transInitDataFile`) are converted in the copy: sound tables (`JAIHostSwapSoundTable`), fx scene table (`FxlineConfig_`, 4 lines x 0x20 bytes per scene). `JAIBasic::~JAIBasic` (declared, never defined in the decomp) is defined under TARGET_PC.
- **Sound info table** (SE + sequence + stream records in one table, 1963 x 0x10 bytes): header u8 formats at 0..3, u16 count at 4, 18 x {u16 count, u16 first index} at 6, records at 0x50 {u32 swBit, u8 priority, u8 track, u16 offsetNo, f32 pitch, u8 volume, u8 fxmix}. Swapped once in the fresh copy (or after `Dvd::loadFile` in `initInfoDataWork`/`reloadInfoDataWork`).
- **Stream list** (`FabricatedStreamEntry`): 0x40 bytes on disc (0x10 unknown, file name, the 0x20-byte AFC header); the console declaration stops at 0x30 (works for entry 0 only), the host one is 0x40. `JAInter::StreamLib::__start` swaps its own copy of the header; the PCM path byte-swaps samples; ADPCM is byte-wise. The decoded `loop_buffer` holds host-endian s16 (read by the mixer as such).
- **IBNK** (`BNKParser::createBasicBank`): `DiscXX` members, so the AAF copy is never touched. Oscillator envelope tables (s16 triplets mode/time/value ended by mode > 0xA) are copied and converted to host s16 (`HostFmt::oscTableToHost`, idempotent by content: every real mode is below 0x100, so the terminator triplet tells the byte order). `registBankBNK` reads the virtual bank id with `rdbe32`. **WSYS** (`WSParser`): same, `TWave` -> host `TWaveInfo` (`mLoadFlagPtr` is a real pointer, so the host struct is bigger than `Driver::Wave_` on the console). Sample bytes stay big-endian in ARAM.
- **BARC** (`Vload::initHeaderM`): header 0x20 + `count` x 0x20 entries (u16 link, u32 offset, u32 size swapped once; marker = the header word at 0x8, which holds the unused memory-file pointer on the console and stays `u32` on the host so `arc[index + 1]` addressing keeps working).
- **.bas** (`JAIAnimeSound::initActorAnimSound`, the single entry for all 8370 files): count and 5 words per 0x20-byte record swapped in place, marker byte `unk2[5]` (0 on disc, 0xDE after) because the same resource is handed in at every animation change.
- **Sequences** (`.bms`): operands are assembled byte by byte (`TSeqCtrl`), nothing to convert. The disc sequences use no `OscFull/SimpleEnv/FIRSet/EXTSet` command (static scan of all 48 sequences), the code paths are host-correct anyway (`oscTableToHost`, FIR coefficients read with `rdbe16`). `cmdNoteOn` decodes the command byte by hand (MWCC bitfields are MSB-first). A jump through an address register logs once and is ignored.
- **Other host fixes**: `JASystem::Dvd::openDvd` fell off the end of a non-void function (returned the DVDOpen/DVDFastOpen BOOL on the console); `JAISystemInterface` overlays `TPortArgs` by console slot number (host slot shift); the init-file name strings are writable buffers; saturating float -> u32 for SE priorities; `MSound` heap doubled (host object sizes).
- **Check**: `python tools\fmtcheck\audio_check.py <build name>` (builds `tools\fmtcheck\audio_check.exe` from the real readers in `sms_game.lib`, LLVM_BIN must point at clang-cl) compares what the host structures contain with an independent big-endian parse of the same disc bytes: AAF (2043 lines: 1963 sound infos, 18 category ranges, bank/wave records, stream header, 3 scenes, fx lines), 13 banks / 564 instruments / 565 oscillators / 1130 envelope tables / 26 drum sets, 3 wave banks / 1678 waves, BARC 48 entries (converted twice), 8370 .bas / 36128 records (initialised twice), oscillator conversion idempotence, 3003 sequence operand reads; plus layout consistency (blobs inside the AAF without overlap, every wave inside its `.aw`, stream header equals `title.afc`'s): 0 differences. Not covered: runtime playback.

## Host DSP (JAudio1 mixing: `src/sdk/dsp_glue.cpp`, `dsp_mixer.cpp`)

The GameCube DSP microcode of JAudio1 is not part of the decomp, so the port replaces `JSystem/dspproc.c`, `dsptask.c`, `osdsp.c` and `osdsp_task.c` (all excluded) with a DSP on a host thread.

- **Protocol** (`dsp_glue.cpp`): `DspBoot(cb)` starts the thread; `DsetupTable` hands it the 64 voice blocks, the resampler table (`DSPRES_FILTER`), the ADPCM table and the 4 effect lines, and returns when the DSP's `0xF355 << 16 | 0x8100` mail has run through `DspFinishWork` (same completion ring as `dsptask.c`). `DsyncFrame2` opens a frame (7 subframes, two output buffers, master level 4.12). Every `DSPReleaseHalt` renders one 80-sample subframe of the voices in its bit map (bit 63 = voice 0) and interrupts the CPU with `0xF355FF00 | subframes left`; the request callback (`JASAudioThread::syncDSP`) runs on the DSP thread with interrupts disabled and turns it into message 1 of the audio thread. The audio thread paces the DSP (it only asks for a frame once the AI DMA consumed one), so there is no DSP clock. `SUNSHINE_DSP_TRACE=1` logs every command and interrupt to stderr.
- **Not emulated**: the hardware mailbox words (commands are typed values, so buffer addresses stay 64-bit), the DSP task scheduler (CARDUnlock's DSP program), the 0xDCD10000 boot handshake.
- **Representation**: `DsetupTable`/`DsyncFrame2` take `uintptr_t` (widened in `dspproc.h`). In a `DSPBuffer`, wave voices keep an ARAM byte address zero-extended in `baseAddress` and sample indices in `loopAddress`/`endPosition`; stream voices (`samplesSourceType 0x21`, `JAIGFrameStream`) hold real host pointers to a host-endian s16 ring buffer and 16.16 positions. Wave data in ARAM stays big-endian as loaded from the disc. The first `DsyncFrame2` buffer receives the right channel (bus 0x0D60), the second the left (bus 0x0D00): `Kernel::vframeWork` interleaves the second one first.
- **Implemented** (`dsp_mixer.cpp`): 4-bit DSP-ADPCM (bit-exact against `tools/dsp_ref.py`), PCM8/PCM16, loops with ADPCM history restore, ring-buffer stream voices (`remainingLength`, `samplesBeforeLoop`), oscillator voices (square, saw, triangle, sine), 4-tap/64-phase resampler from `DSPRES_FILTER`, FIR/IIR filter modes, 6 mixer channels per voice with linear 80-sample volume ramps into the buses, `endRequested`/`done`, pause, effect lines, master level.

## Sequence interpreter on the host: register file and table indices (`JASTrack`, `JASSeqParser`, `JASRegisterParam`)

- **What the console register file is** (from `JASTrack.s`, `readRegDirect`/`writeRegDirect`/`writeRegParam`): every register access outside the special ids is `lhz/sth 0x280 + 2 * id` on the track, i.e. the register file is `u16 regs[id]` starting at `TTrack::mRegisterParam`. Ids 0x00-0x17 lie inside the 0x30-byte `TRegisterParam` (0-5 `unk0[]`, 6 bank<<8|program `unkC`, 7 `unkE` (pitch), 8-12 the five pan powers, 13 `unk1A`, 14/15 the halves of `unk1C`, 16-23 the halves of `unk20[4]` with the even id = high half because the console is big-endian), 0x18-0x1F in the 16 bytes behind it (`unk2B0`). From id 0x20 on the console runs into `mParent` and `mChildren[]`: 0x20/0x21/0x22 (bank, program, composite), 0x2C/0x2D/0x30 (child-active bits, note-off bits, loop count) are special-cased reads, 0x28-0x2B are the four address registers (`unk20[]` as `u32`, `readReg32`/`setAddress`), 0x23 is r4:r5 in `readReg32`, 0x2E/0x2F are write-only byte halves of register 13 in `writeRegParam`. Any other id above 0x1F is not a register: on the console it overwrites a track member.
- **Host fix**: `TRegisterParam::getReg/setReg` map the ids explicitly (with the big-endian half order for 14-23, 8 spare registers `mSpare` for 0x18-0x1F); `readRegDirect`, `writeRegDirect` and `writeRegParam` use them instead of `unk0[id]`. Ids 0x2E/0x2F read and write as the low/high byte of register 13 on the host (the console reads a child pointer there; `writeRegParam` reads the destination first, which is why shipped sequences read them). An id that is none of the above is reported once on stderr, reads 0 and drops the write (`TRegisterParam::sBadAccessCount`, test hook `sAccessHook`). The corruption seen at run time (a 0x78 landing in the high half of `mChildren[2]`) is an access to id 0x2E on the old layout: host offset 0x5C of `TRegisterParam`.
- **Other u8/u16 indices into small tables** (same class): ports (`TTrackPort`, 16: `TTrackPort::inRange`), timed parameters (`writeTimeParam`, 18), child tracks (`cmdCloseTrack`, `cmdChildWritePort`, 16), interrupt slots (`cmdSetInterrupt/DisInterrupt`, 8), oscillator route (2), pan switch tables (7), IIR cutoff table (128 rows), plus a null child from an exhausted track pool in `cmdOpenTrack/Bros`. Each drops the command and logs (first 8 occurrences). `TTrack::mainProc` read an uninitialised `r31` after `goto bail`; it is zero on the host.
- **Check** (`python tools\fmtcheck\audio_check.py <build name>`, mode `replay`): all 48 sequences of `sequence.arc` run 6000 ticks each through the real `TTrack`/`TSeqParser` (no DSP, banks unregistered so a note stops at the bank lookup; ports poked every 40 ticks): 0 accesses outside the register file (registers touched: read 0,3,6-12, write 0,3,6-13), no table-index report, and the 185-track pool is full again after every sequence. Not covered: values the game feeds through the sync callback and the banks (note-on path).

## File formats on the host: JPA particle resources (`.jpa`, `JSystem/JParticle`)

Different from the formats above: **the file image is never modified.** `JPAResourceManager::load` hands the `.jpa` bytes of an archive to a loader that copies everything it keeps, so the host reads the big-endian image field by field and converts the copies it keeps. No marker is needed (a resource can be loaded any number of times, `loadParticleMario` loads `ms_itemget1_*` twice) and nothing in the archive buffer changes (the test compares it afterwards).

- **Disc layout** (all 2227 `.jpa` of the disc follow it, 1 exception below): 0x20-byte header `'JEFF' 'jpa1'`, u32 file size, u32 block count; blocks `{u32 magic, u32 size incl. header}` tile the file (sizes padded to 0x20). Content: `BEM1` (emitter, 0xA0), `FLD1`* (field, 0x60), `KFA1`* (key frames: u8 count at 0x10, u8 loop at 0x12, count x 4 f32 at 0x20), `BSP1` (base shape), `ESP1`, `SSP1` (child), `ETX1` (ex-texture), then every `TEX1` (0x20 header with the name at 0xC, 0x20-byte BTI header, image/palette bytes). The loader depends on the TEX1 blocks being last.
- **Readers**: `JPA_U32/JPA_S16/JPA_F32` (`JPADataBlock.hpp`) wrap every raw load of the image (`JPABinaryHeader`, block type/size words, `JPABaseShape/ExtraShape/SweepShape/ExTexShape`, the colour-key table of `makeColorTable`, the `s16` table offsets); on the console they are the original expressions. The BSP1/ESP1/SSP1/ETX1 readers copy scalars out (no pointers into the image), the console `u8*`/`GXColor*` tables become heap copies as before.
- **Kept block copies** (`JPADataBlock`, 0x20-aligned heap copy): `BEM1`/`FLD1` stay big-endian and are read by the typed `JSUInputStream` reads (the three raw `read(&vec, 12)` of `loadBaseEmitterBlock` became typed reads); the block size word is read with `JPA_U32`. `KFA1` key frames are read by `JPAGetKeyFrameInterpolation` as host floats: swapped once in the copy (`JPADataBlock` constructor, by block type). `TEX1`: the BTI header at +0x20 is converted by `JUTTexture::storeTIMG` (`swapResTIMG`, marker 0xDE, see BTI above), image/palette bytes stay raw for GX; the name at +0xC is plain bytes.
- **Pointers**: no 32-bit pointer is stored in the file. Loader/link structures (`JPADataBlockLinkInfo`, `JPAEmitterData`, texture and emitter arrays) are real host pointers from the JKR heaps; `mTextureDataBase` stays `u16[]` of texture-pool indices; `JPABaseEmitter::unk120` (user work) is already `uintptr_t`. `JPAEmitterManager` sizes its three solid heaps from the host `sizeof` (248 / 800 / 168 bytes for particle / emitter / field, console 0xDC / 0x220 / 0x8C; every object is a multiple of 8 so the solid heap's 8-byte alignment wastes nothing): all pooled objects fit (checked: 4000 particles, 16 emitters, 64 fields). A game-size manager (5000 particles, 256 emitters, 512 fields) takes about 1.5 MB of heap where the console used 1.3 MB.
- **Decomp bugs found against the retail asm** (`JPAField.cpp` is `NonMatching`; both fixes are under `TARGET_PC`, the original stays under `#else`): (1) `loadFieldBlock` read an `f32` into `mMaxDistanceSq` where the asm reads the `u16` status at `+0x54` (`stream >> unk54`), then skips 2: every field value after it was 2 bytes off (the data has the strength at block offset 0x14 and the vectors at 0x20/0x2C; the status holds the fade/cone/limit flags, non-zero in 167 of 256 `particle.szs` fields). `mMaxDistanceSq` is computed by `calcMaxDistance()` and never loaded. (2) `JPAConvectionField::affect` redeclared `thing4` inside `if (unk34 != 0)` and normalized the uninitialised inner vector; retail normalizes the outer `thing - thing2` (NaN particle positions on the host before the fix). `loadBaseEmitterBlock` and the `JPAField` read order were compared with the asm; the shape readers are matching units.
- **`__fres` users** (left undefined as agreed, nothing was added): `JPABaseField::calcFieldFadeScale` (2 sites; reached for fields with status 0x20/0x40, 68 of 284 `particle.szs`+`bosshanachanJpa.szs` resources) and `JPAVecToRotaMtx` (`JPAMath.cpp`, called by `calcEmitterGlobalParams` for every emitter whose direction is off the Z axis, 185 of 284 resources). Every particle effect hits one of them while an emitter calculates, so no emitter can run on the port until `__fres` exists; loading, emitter creation and drawing set-up do not need it. Also unreachable but UB if ever called: `JPAConvertFloatToFix` falls off the end of a non-void function (empty decomp stubs, no caller).
- **Disc defect**: `ms_m_spinos.jpa` in `scene/coronaBoss.szs` has a one-byte shift before its TEX1 block (header size 0x840, file 0x858, the block walk reads type `\0TEX`). The loader survives it (no TEX1 found, same as on the console) but the resource has no texture although its shape wants one: drawing it would index `mTexIndices` through a null pointer (address 0 on the console). All other 2226 files are well formed.
- **Check** (`tools\jpa_test.cmd <build name>`, builds `tools\jpa_test.cpp` against the real code in `sms_game.lib`, then `tools\jpa_test.py` parses the raw bytes independently): every `.jpa` of `particle.szs`, `bosshanachanJpa.szs` and `select.szs` (293 files; `--scenes` adds the 107 scene archives, 2227 files in all, decoded by the real `JKRDecomp`) goes through `JPAResourceManager::load`, then `JPAEmitterManager::createEmitterBase` (BEM1, FLD1, `JPADraw::initialize`). 63,264 keys (466,530 with scenes) are compared: every shape field incl. the derived rates and the interpolated colour tables (float32 arithmetic emulated), key frames, the texture header/crc/name dedup and indices, emitter and field values, the untouched block copies; layout checks (blocks tile the file, TEX1 last, table offsets and texture indices inside their blocks, image inside the TEX1 block). Then each emitter runs 8 `calc()` frames (all 2227 emitters, 151,311 peak particles, all finite) with the direction forced to +Z and field fades cleared (the two `__fres` paths), and `TMarDirector::loadParticleMario` runs for real through `JKRGetResource` (114 resources, 55 textures). Test-local only: the GX texture-object setters are recorded by stand-ins (Aurora's live in the renderer library). Not covered: drawing (`JPADraw*` need the GX backend), the `JPAEmitterManager` against the game-size heap, anything that needs `__fres`.

## THP movies on the host (`THPPlayer/*.c`, `dolphin/thp/*.c`, `System/MovieDirector.cpp`)

The decomp's own decoder is built (`dolphin/thp/` is no longer in `excluded-units.txt`, `AURORA_ENABLE_THP` is OFF) because Aurora's `THPDec.cpp`/`THPAudio.cpp` deliberately differ from the console: its IDCT fixes the SDK's quarter-IDCT quirk (see below) and its audio rounds ties up. Everything is `TARGET_PC` with the original kept under `#else`; the six units compile with MWCC to objects byte-identical to the HEAD sources.

- **Container (big-endian)**: `THPPlayerOpen` swaps the 11 header words after the magic (`frameRate` is an `f32` stored the same way), `numComponents`, the video info (3 words) and the audio info (4 words) once, after the `memcpy` out of `WorkBuffer`; `THPPlayerPrepare` swaps the two offset-table words of the random-access path. The per-frame words (next-frame size, component sizes) stay in the file buffer and are read through `THP_RD_S32/THP_RD_U32` (`THPPlayer.h`: `rdbe32` on the host, the plain load on the console) in `THPRead.c`, `THPVideoDecode.c` and `THPAudioDecode.c`. The frame buffers are never modified, so the movie can loop.
- **Audio**: `THPAudioDecode` swaps a copy of the 0x50-byte record header (`THPSwapAudioHeader`, coefficients and `yn` history are `s16`); the nibble stream is bytes. The arithmetic is the SDK's integer code unchanged (round to nearest, ties to even on the 16.16 value, saturate). Output slot 0 is the SDK's "right" pointer and slot 1 its "left" one (`decRightPtr = audioBuffer`, `decLeftPtr = audioBuffer + 1`): the first stored channel lands in the odd slot, exactly as on the console. ffmpeg's `adpcm_thp` puts the first stored channel in slot 0, so the two differ by a channel swap (30 LSB max otherwise, ffmpeg rounds differently); whether slot 0 is the left speaker depends on the AI order assumed by `av.cpp` for all audio (JAudio and THP alike) and is not verified against hardware.
- **Video decode** (`THPDec.c`, `#ifdef TARGET_PC`): no locked cache and no GQRs on the host (`PPCMfhid2` check, `LCQueueWait`/`LCStoreData`, `THPInit`'s LC bases, `__THPGQRSetup/Restore` are skipped; the MCU rows are written straight into the output planes). The inverse DCT is a line-by-line transliteration of the paired-single assembly (`THPps`: one function per `ps_*` instruction, the same order, `ps_madd/msub/nmsub` as `fmaf`, `#pragma clang fp contract(off)` so nothing else fuses; `psq_st` with GQR6 = scale 2^-3, saturate, truncate). The row pass keeps the assembly's four paths (DC only / first two / first four / regular coefficient test) because they are not numerically identical to each other. The Huffman decoder walks the canonical `maxCode/valPtr` tables bit by bit over the same 32-bit-word stream state (`currByte`, `cnt` 1..33) instead of the 5-bit lookup in assembly; `__THPPrepBitStream` starts the stream at the unaligned byte (the console aligned down to a word and skipped bits, same bit sequence). 64-bit: `THPHuffmanTab.Vij`, `THPFileInfo.c/dLC` are real pointers (`sizeof(THPFileInfo)` 1776 on the host, the 0x1000 work area still fits, asserted by the test), the Huffman code scratch table is aligned to 2 bytes instead of `+257`.
- **The SDK quirk is kept**: the `_quarterIDCT` row path (only coefficient 1 non-zero besides DC) stores output columns 3 and 4 swapped. Aurora has a `kBuggyQuarterIdct = false` switch for it; the port keeps the console behaviour. Visible as up to 12 LSB against ffmpeg on edges; with the swap undone the same model is within 1 LSB of ffmpeg (int and float IDCT), which also proves the model and the Huffman/IDCT structure are right.
- **MovieDirector**: the decompiled `setParams(W - xSize / 2, H - ySize / 2, ...)` is not what the asm does (`8010BD64..8010BD94`: `x = (W - xSize) >> 1`, `y = (H - ySize) >> 1`); on the host the asm version is used, the original expression stays under `#else` (that unit is NonMatching and not in the DOL). Without it the quad lands at x = 320, y = 320 or further and is mostly off-screen.
- **Threads and timing**: the player runs on the real OS layer unchanged. Video decode, audio decode and the reader are `OSCreateThread` threads (priority 20/12/8, started with `OSResumeThread`), `PlayControl` is the VI post-retrace callback (non-blocking message calls only, as `os_thread.cpp` requires), the audio is pulled by the JAudio mix callback (`registerMixCallback(..., 3)`, one 560-frame block per DAC frame). The movies use `videoType` 0: one new frame per `retrace * frameRate / 5994`, i.e. every second retrace.
- **Draw** (`THPDraw.c`, no change): three `GX_TF_I8` textures (Y, U/2, V/2; the decoder writes the 8x4 tile order GX expects), a 4-stage TEV with a signed S10 register (-90, 0, -114, 135) and K colors (0,0,226,88), (179,0,0,182), (255,0,255,128) that computes R/G/B from alpha-carried G. Aurora supports every call it makes (`GXSetTevColorS10` sign-extends 11 bits, `GXSetTevKColor(Sel)`, swap tables, `GXInitTexObjLOD`, `GXPosition3s16`/`GXTexCoord2u16`). Textures are keyed by content hash and converted/copied while the command processor runs, which `GXDrawDone` (`THPPlayerDrawDone`) waits for before the texture sets are recycled, so the missing `DCInvalidateRange` is harmless. Not executed on a GPU in this task.
- **Checks**: `tools\thp_test.cmd [movie] [frames] [first frame]` builds the decomp decoder alone, decodes real frames and compares them (`tools\thp_ref.py`) with an independent float32 model of the assembly (own JPEG parser, canonical Huffman, exactly rounded fma): max error 0 on Y/U/V for `openingA` (8 frames), `EX128x144_q0`, `Entrance`, `autodemoA`, `openingBA` (frames 1200..1203), `Entrance` (1500..1503); audio equals an integer re-implementation of the SDK algorithm (max error 0); ties round half-up in Aurora's decoder would change 135..144 of ~8500 samples (max 7..16). `tools\thp_player_test.cmd [movie] [retraces]` runs the whole player (`THPPlayer.c`, `THPRead.c`, `THPVideoDecode.c`, `THPAudioDecode.c` with the real `os_thread.cpp`, `av.cpp` retrace and AI code; DVD and GX replaced by test doubles) for N retraces: every frame it hands to the renderer is bit-identical to a direct decode, frame numbers never go backward, 29.8 frames/s (movie 29.97), and the audio pulled through the mix callback equals `THPAudioDecode` sample for sample (`openingA`, `Entrance`, `autodemoA` 0 differences; `EX128x144_q0` has no audio). Decode time 0.7 ms (640x320) to 2.3 ms (640x448) per frame.
- **Not verified**: the picture on screen (the first boot-smoke runs never presented a frame during the movie, see the next point), the channel order of the audio on the speakers, `onMemory` mode (the game never uses it), restart markers (no movie has one, the decoder keeps the console code), movies other than the ones listed above.
- **Found while booting** (fixed by the lead): `TDisplay` runs with a single XFB in the movie scene, so `VISetNextFrameBuffer` was called once and `aurora_end_frame` never again; the unended Aurora frame overflowed its 24 MiB uniform buffer after ~44 s (`abort()` in `lib/gfx/recording.cpp`, a silent 0xC0000409). THP played correctly up to that point (audio callback at the DAC rate, textures recycled, `THPPlayerPlay` after the fade-in).

- The remaining differences are inline decisions, stack frame sizes and register allocation; logic, constants and call order were checked against the asm for every function below ~95%. Recurring causes: (1) retail calls `TUtil<f32>::mod`/`std::fmodf` (both are the same weak function body, see below), `TVec3::dot`/`scale(f32, const TVec3&)`, `TRotation3::identity33`/`setQuat`, `TBathtub`/`TWaterGun::getCurrentNozzle` and `TSpineBase::pushNerve` out of line where MWCC inlines them here (`#pragma dont_inline` has no effect, see the MapObj notes); (2) in the original the `TNerveBase<TLiveActor>::TNerveBase()` constructor of an inlined `theNerve()` static stays a call, here it is inlined; (3) retail reads `unk38` of the managers around a few calls and drops the result (not reproducible, same as `BathtubKiller.cpp`); (4) `TParamRT<f32>::get()` after a virtual `getSaveParam()` is folded into the load in retail but kept as `addi` + `lfs 0x10` here when the value stays live across another call.
- **`std::fmodf` and `JGeometry::TUtil<f32>::mod` (shared headers).** The retail weak `fmodf__3stdFff` (in `MapObjCorona.s`) and `mod__Q29JGeometry8TUtil<f>Fff` (in `koopajr.s`) have the same body: `if (|y| > |x|) return x; return x - y * (f32)(s64)(x / y)` with a float divide. `MSL_C/math.h` defined `std::fmodf` as `::fmod` on doubles, so every user compiled to a `fmod` call; it now has the retail body, and `TUtil<f32>::mod` (`JGUtil.hpp`, needed by `Koopa.hpp`/`koopajr.cpp`) was added with it. Only the unfinished/non-matching users (`Koopa`, `wireTrap`, `BathtubPeach`, `koopajr`, `MapObjCorona`) call either. Both are in the PCH path (`math.h` and `JGUtil.hpp` are pulled in by `SMS.pch`), so a PCH rebuild is needed to see the change in single-unit MWCC compiles. The host build uses the CRT's `fmodf`; it differs from the retail truncating formula only in the last bit of quotients that round up to an integer.
- **How the match percent was reached (reusable MWCC findings).** (a) MWCC (`-inline deferred`) emits functions in reverse definition order; these sources define functions in reverse of the asm `.text` order. (b) `#pragma auto_inline off` is read at the *definition of the callee*, also in deferred mode: `koopajr.cpp` turns it off for the whole file and back on around the tiny `TDirectionCalc` helpers, which is what makes `calcNearerDirection`/`appearShineKiller`/the `TKoopaJrSubmarine` constructor stay out of line and `d2r`/`r2d`/the `TDirectionCalc` constructors inline like retail (about +10 points over the default). `#pragma inline_depth(N)` is file-global (the last value wins): `limitkoopa.cpp` would gain about 6 points overall with `inline_depth(4)` (`loadAfter` 26 to 100, because the parts constructor chain only inlines at that depth) but loses 25/9 points in `bind`/`startHipDrop`, so it is not applied; `koopajr.cpp` gets worse with it. (c) The global math.h wrappers `sin(float)`, `cos(float)`, `atan2(float, float)` (not `sinf`/`cosf`/`atan2f`, not `std::`) reproduce the retail call shapes and argument order of `TDirectionCalc` exactly (those functions reach 100%). (d) Call arguments are evaluated right to left, so a value that retail loads first needs a local (`f32 height = ...; initHitActor(..., radius, height)`); `TCallbackHitActor` therefore takes radius and height as constructor arguments and has an inline constructor in the header, because retail inlines it twice into `TKoopaJrSubmarine::init`. (e) Comparison form changes the branch shape: `if (!(a < b))` instead of `a >= b` (one `blt` instead of `cror` + `bne`), and an `if` chain instead of a `switch` on `mKillerIndex % 4`; `mKillerKinds` is signed (`s8`) because retail compares it with `cmpwi`. (f) A function-local `static const char* onetimeFilenames[1]` plus a one-iteration `SMS_LoadParticle` loop reproduces the particle loader of `TKoopaJrManager::loadAfter` (100%).
- **Header changes.** New: `KoopaJr.hpp` (`TKoopaJr` 0x170, `TKoopaJrSubmarine` 0x1AC, managers, params, nerves), `DirectionCalc.hpp` (`TDirectionCalc`, one `f32` at 0x0, defined in `koopajr.cpp`; used by `limitkoopa`/`limitkoopajr` through `bl`), `LimitKoopa.hpp` (`TLimitKoopa` 0x1C8, `TLimitKoopaParts/Body/Head/Hand/Flame`, manager 0x54), `LimitKoopaJr.hpp` (`TLimitKoopaJr` 0x17C), `TinKoopa.hpp`, `Seal.hpp` (`TSeal` 0x154, `TSealManager` 0x54). `Rocket.hpp` keeps `TRocket(const char* = "ロケット")`, `isAttack()` and the inline destructor and adds `TRocketManager`, the params and the nerves.
